How the interview-prep system fits together

Every script and data file built so far, and how they connect — from the 8 markdown source files down to the one decision the router hands back.

an LLM call happens here (Groq or Gemini) pure deterministic code — no AI involved a stored data file

Stage 1Building the corpus

Turns 8 hand-written markdown files into one structured, richly-tagged JSON record — the thing every later phase reads from.

deterministic parse_qa_markdown.py

Splits each markdown file on its ## Q<N>: headings into question/answer pairs. Pure text parsing, no AI.

Groq tag_difficulty.py

Sends a topic's questions to the LLM together, asking it to sort each into foundational / intermediate / advanced, with reasoning before the answer to keep judgments consistent.

orchestrator build_tagged_corpus.py

Runs the two files above per topic, in safely-sized batches, saving progress after every batch so a failure never loses work already done.

Groq tag_prerequisites.py

A second LLM pass: for each question, which other specific questions in the same topic does it depend on? Produces the raw, unvalidated edges.

deterministic prereq_graph.py

No AI at all. Validates the LLM's edges (drops hallucinated references, self-references, tier violations) and turns the result into an actual study order — with a guaranteed way to detect circular dependencies.

orchestrator build_prereq_graph.py

Runs the prerequisite pass per topic, validates, and writes the cleaned dependency list onto every entry in tagged_entries.json.

Stage 2Making the corpus searchable

Turns each entry into a vector so it can be found by meaning later — built, but nothing downstream reads it yet.

Gemini build_embeddings.py

Embeds every question+answer pair, normalizes the vectors, and stores them in a FAISS index alongside a matching metadata file — the retrieval half of RAG, waiting for Phase 5's generation half.

Stage 3Tracking real progress

Completely independent of the corpus files above — this is what actually changes every time you study something.

deterministic tracking_db.py

An append-only log: every study/quiz attempt gets its own row. "Current status" is just whichever row is most recent for that item — never a separately-maintained value that could drift out of sync.

Stage 4Deciding what's next

Where both inputs meet. Reads the corpus's tiers and prerequisites, reads the tracker's real history, and picks one thing to do.

deterministic routing_graph.py

gather_state() assembles one topic's questions with their live status and readiness; decide() applies the four-bucket priority (struggled → quiz → new → review) with the tier-then-number tiebreak; get_topic_progress() tallies status counts per department. No LLM call anywhere in this file — the routing decision itself is fully deterministic, built entirely on data the earlier stages produced.

What's still a stub: the embeddings branch has no reader yet, and the four decision actions (study_new, quiz, review_struggled, review_solved) currently just report themselves — turning them into real generated explanations and quiz questions, grounded in the FAISS index, is exactly what Phase 5 wires up next.
